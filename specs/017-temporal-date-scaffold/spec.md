# Feature Specification: 确定性日期脚手架(TIMELINE 块)

**Feature Branch**: `017-temporal-date-scaffold`

**Created**: 2026-07-27

**Status**: **收口 —— US1 PASS(实现正确、默认关);US2 端到端门 NO-GO(2026-07-27)**

> **Verdict**:三臂 8-rep 配对实测 temporal **+0.62pp,McNemar χ²=0.154 / p=0.845(ns)**,
> 且**小于同配置 `ref` 噪声标尺 0.93pp**;点火率 100%、token +16.0%。
> 归因 = **落在噪声内**(非"没点火"、非"上下文被稀释")。`--temporal-date-scaffold` 维持默认关、
> 不出货。完整 verdict 与五项数字:[`docs/locomo-score-levers.md`](../../docs/locomo-score-levers.md)
> 「确定性日期脚手架(Feature 017)」节。

**Input**: User description: "先做收益高的" —— 经核实 C1(judge 口径补齐)已由 spec 007 落地、不需要立项后,从 [`docs/locomo-score-levers.md`「剩余未验方向盘点」](../../docs/locomo-score-levers.md) 四项中选定台账上限最高的一项:**确定性日期脚手架(014 Option B,TIMELINE 块)**,temporal 答题侧 38 题 ≈ 2.47pp 名义上限。

## 背景

engram 的 LoCoMo temporal 类(category 2)是当前诚实参考点下的次弱类。**检索侧已探尽、答题侧 prompt 已两连败**:

| 已判死的路 | 结论 |
|---|---|
| 013 检索侧时间窗召回臂 | NO-GO(`ParseTemporalIntent` 仅 19.6–29.6% 时序 query 点火) |
| 014 强化时序推理契约(四锚重 CoT) | NO-GO(**翻车**,显著差于旧简单契约) |
| 014b old-tplan 8-rep 确认 | ns,inconclusive,`--temporal-answer-prompt` 维持默认关 |
| temporal 检索改进(免费覆盖门) | gold 中位 rank **3**、`oracle_lift@30` = **0.000**,零可得空间 |

2026-07-24 近免费离线分诊把 temporal 55 道错题切成两半:

- **38 题(69%)gold 已在 top-30 答题上下文里却答错 = 答题侧瓶颈**;
- 17 题(31%)埋在 top-30 外 = 召回侧,其中仅 8 题现解析器能点火 ⇒ 召回侧最多救 ≈1.5% temporal,舍入级。

答题侧 38 题的失败模式分布:

| 模式 | 题数 | 占比 |
|---|---:|---:|
| **±1 月/年误归属 / 多候选去歧失败** | 21 | 55% |
| **相对表达未解析成绝对**("next month" 被原样回显) | 10 | 26% |
| **时长 / 区间算术未执行**("how long" 两端点都在上下文却没相减) | 7 | 18% |

**本 feature 的立论**:014 证明了"让模型自己按契约推理"这条路走不通(强化契约反而更差)。剩下的路是**用确定性代码替代模型能力**——把日期抽取、规范化、排序、相对→绝对解析、区间算术这些**机械步骤**在注入答题上下文之前就由代码算好,模型只做选择,不做日期算术。

**新证据支持靶心正确**(2026-07-26 answerer-parity 探针):temporal 错题 **66% 可被更强的答题模型翻正**(四类中最高),即这 38 题的失败是"模型算不动日期"而非"信息不在上下文"——正是确定性脚手架要替代的那部分能力。

**定位诚实点**:答题步活在评测 harness(`cmd/locomo-bench`,host 侧),**不是 engram 引擎能力**。引擎只做存储/检索/抽取。因此本 feature 引擎零改,交付的"可移植性"形态是一份**文档化的脚手架 pattern**,任何集成方可抄进自己 host 的答题步。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 确定性 TIMELINE 脚手架 + 离线断言 (Priority: P1)

维护者在答题上下文构造阶段增加一个**确定性预处理步**:扫描本次要喂给答题模型的全部检索记忆,抽出每条的绝对事件日期,规范化、按时间升序排序、编号,并把候选间的关键时间差预先算好,组装成一个 `TIMELINE:` 块附在答题上下文中。整个过程**零 LLM 调用、纯确定性代码**,同一批记忆永远产出逐字节相同的 TIMELINE。开关默认关,关时答题上下文逐字节不变。

**Why this priority**: 这是整个 feature 的全部机制,且**零成本可完整验证**。脚手架的正确性(日期抽没抽全、排序对不对、算术准不准、降级会不会臆造)完全可以用离线单测钉死,不花一分答题钱。没有这一层,US2 花钱跑出来的任何分数都无法归因——分低了不知道是"脚手架思路错"还是"脚手架实现有 bug"。

**Independent Test**: 用手工构造的记忆集合(含完整日期、缺日期、相对表达、跨年、同日多条)驱动脚手架构造函数,断言产出的 TIMELINE 块内容、排序、编号与算术逐字节符合预期;断言开关关闭时答题 prompt 与当前实现逐字节一致;`CGO_ENABLED=0 go test` 全绿;`git diff --name-only -- memory embedding provider store internal` 为空。全程零 LLM 调用、零 box 依赖。

**Acceptance Scenarios**:

1. **Given** 脚手架开关关闭(默认),**When** 构造任意类别的答题上下文,**Then** 上下文与当前实现**逐字节一致**,且 run fingerprint 不含脚手架标记。
2. **Given** 开关打开且题目类别为 temporal,**When** 检索记忆中有 5 条带绝对事件日期,**Then** TIMELINE 块按日期升序列出这 5 条、连续编号、日期以统一规范格式呈现。
3. **Given** 开关打开,**When** 某条记忆**没有**可解析的事件日期,**Then** 该条**不进** TIMELINE 块也**不被丢弃**(仍在正文记忆列表中),脚手架**不臆造**任何日期。
4. **Given** 开关打开,**When** 某条记忆正文含相对时间表达且该条自带绝对锚日期,**Then** 脚手架用该锚解析出绝对日期并在 TIMELINE 中标注为推导值(与原生日期可区分);**When** 无锚可用,**Then** 不解析、不标注、不臆造。
5. **Given** 开关打开且 TIMELINE 中有 ≥2 个日期,**When** 组装脚手架,**Then** 预先算好的时间跨度(首尾间隔、相邻间隔)随块一同呈现,数值可被单测精确断言。
6. **Given** 开关打开但题目类别**不是** temporal,**Then** 该题答题上下文逐字节不变(类别门控,构造上不伤其他类)。
7. **Given** 同一批记忆输入两次,**When** 分别构造 TIMELINE,**Then** 两次产出**逐字节相同**(确定性,无随机、无时钟依赖)。
8. **Given** 开关打开,**When** 生成 run fingerprint,**Then** 追加脚手架标记,与未开脚手架的 run 不同 ⇒ 不会被静默配对或复用缓存。

### User Story 2 - 端到端 GO/NO-GO 门 (Priority: P2,门控:US1 交付 + 显式成本授权)

在 US1 已用离线断言证明脚手架正确之后,维护者在**显式成本授权**下,于全本地栈上跑一次多臂对跑,用 **temporal 类端到端答题准确率**判定脚手架是否真的把那 38 题救回来,并确认没伤到其他类别。

**Why this priority**: 有价值但花钱、且依赖 US1 先证明实现正确。**008 铁律**(覆盖率/中间信号增益 ≠ 答题增益)在本项目已连续成立 N 次,因此 verdict 只认端到端答分。默认不执行。

**Independent Test**: 授权后在同一 run 内跑对照臂与处理臂,产出 temporal 类配对显著性检验 + overall 回退检查 + prompt token 增量实测,落 tracked verdict。

**Acceptance Scenarios**:

1. **Given** US1 已交付且成本已授权,**When** 执行 e2e 门,**Then** 至少包含 `base`(脚手架关)与 `scaffold`(脚手架开)两臂,**且**包含一条与 `base` 配置完全相同的**噪声标尺重跑臂**(无它则任何单臂对单臂差值不可信)。
2. **Given** e2e 门跑完,**When** 判定,**Then** GO 判据 = temporal 类配对检验**显著抬升** **且** overall **不回退**;二者任一不满足即 NO-GO。
3. **Given** 判定为 GO,**When** 收口,**Then** 声明新参考点、脚手架 pattern 文档化为可移植答题契约、eval 结果**单独提交**(与算法改动分离提交,宪法 IV)。
4. **Given** 判定为 NO-GO,**When** 收口,**Then** 落带**归因**的 NO-GO verdict 于 tracked docs(区分"思路错"vs"上下文被稀释"vs"落在噪声内"),开关维持默认关,不产出移植文档。
5. **Given** 使用租用 GPU box,**When** 跑首臂,**Then** 冷启动首臂结果按既有纪律**丢弃/复跑**,配对检验只对干净复跑基线做,绝不对冷首臂做。
6. **Given** e2e 门跑完,**When** 记录,**Then** 同时报告脚手架带来的**答题上下文 token 增量**,用于判断收益是否来自"信息重组"而非"喂了更多内容"。

### User Story 3 - Verdict 与台账回填 (Priority: P3)

无论 GO 还是 NO-GO,把结论、归因、成本、产物指针落进 tracked 文档,使下一个人不必重跑就能知道这条路的结局。

**Why this priority**: 本项目已有明确纪律——实验结论必须落 tracked docs 而非只进会话记忆(换环境会丢)。这是每个杠杆 feature 的收口动作,零成本但不可省。

**Independent Test**: `docs/locomo-score-levers.md` 新增本 feature 的 verdict 节,含判据、数字、归因、成本、产物位置;「剩余未验方向盘点」表中本方向的状态被更新。

**Acceptance Scenarios**:

1. **Given** US2 出结果,**When** 收口,**Then** tracked docs 记录 verdict + 归因 + 实测成本 + 产物指针,且**不含任何凭据**(主机地址/端口/密码/API key 一律不入库)。
2. **Given** verdict 落定,**When** 更新台账,**Then**「剩余未验方向盘点」中本方向从「未验」改为对应结局,四项剩余数同步修正。

### Edge Cases

- **全部记忆都没有可解析日期** → TIMELINE 块整块省略(不输出空块、不输出占位符),答题上下文退化为当前形态。
- **只有 1 条记忆有日期** → 输出单条 TIMELINE,**不输出**任何时间跨度(无从相减),不臆造第二个端点。
- **同一日期多条记忆** → 并列呈现,排序在同日内保持原有检索顺序(确定性,不引入次级随机排序)。
- **跨年 / 跨世纪日期** → 正常参与排序与算术,不因年份边界出错。
- **日期格式异常或不完整**(只有年、只有年月) → 按可解析的最粗粒度参与排序,算术在粒度不足时**不给出**精确天数,降级为粗粒度表述,绝不补零假装精确。
- **相对表达解析失败** → 静默跳过该条的推导,不报错、不中断、不臆造,原文仍在正文记忆列表里可被模型自行阅读。
- **TIMELINE 块过长**(候选记忆数很多) → 有明确的长度上界策略,且该策略被记录、可被断言,不做静默截断。
- **脚手架开启但答题模型忽略 TIMELINE** → 这是 US2 要测的真实风险之一(014 的翻车模式:给模型更多结构反而让它想太多),NO-GO 归因必须能区分这一种。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在答题上下文构造阶段提供一个**纯确定性、零 LLM 调用**的日期脚手架步骤,对同一批输入记忆产出逐字节相同的输出。
- **FR-002**: 脚手架 MUST 从每条检索记忆中抽取其绝对事件日期,并以统一规范格式呈现;抽取失败的记忆 MUST 被跳过而非丢弃,且 MUST NOT 被赋予任何臆造日期。
- **FR-003**: 脚手架 MUST 将有日期的候选按时间升序排序并连续编号呈现,使答题模型无需自行抽取和排序日期。
- **FR-004**: 脚手架 MUST 在记忆正文含相对时间表达且该记忆自带绝对锚日期时,用该锚确定性地解析出绝对日期,并在呈现上与原生日期**可区分**;无锚时 MUST NOT 解析。
- **FR-005**: 脚手架 MUST 在候选日期 ≥2 个时预先计算并呈现关键时间跨度(至少含首尾间隔),使答题模型无需自行做日期减法。
- **FR-006**: 脚手架 MUST 由一个**默认关闭**的开关控制;关闭时答题上下文 MUST 与当前实现逐字节一致。
- **FR-007**: 脚手架 MUST 仅对 temporal 类题目生效(类别门控);其他类别的答题上下文 MUST 逐字节不变。
- **FR-008**: 开关开启时,run fingerprint MUST 追加可识别的脚手架标记,使不同口径的 run 不被静默配对或复用缓存。
- **FR-009**: 系统 MUST 提供离线、无网络、无 box 依赖的确定性测试,覆盖排序、编号、规范化、相对解析、区间算术、缺日期降级、类别门控与开关关闭时的零差异。
- **FR-010**: 本 feature MUST NOT 修改引擎目录(`memory/ embedding/ provider/ store/ internal/`)下的任何文件;验证方式为 `git diff --name-only -- memory embedding provider store internal` 输出为空。
- **FR-011**: 端到端验证 MUST 以 temporal 类**答题准确率**作为唯一 verdict 依据;覆盖率、命中率等中间信号 MUST NOT 用作 GO 判据(008 铁律)。
- **FR-012**: 端到端验证 MUST 包含一条与基线配置完全相同的重跑臂作为噪声标尺,且配对检验 MUST NOT 对冷启动首臂进行。
- **FR-013**: 端到端验证 MUST 实测并报告脚手架引入的答题上下文 token 增量。
- **FR-014**: 端到端验证 MUST 在显式成本授权后才执行;未授权时 MUST NOT 产生任何答题成本。
- **FR-015**: 结论(GO 或 NO-GO)MUST 落入 tracked 文档并含归因;凭据 MUST NOT 出现在任何文档、日志或产物中。
- **FR-016**: 若判定 GO,eval 结果 MUST 与实现改动**分开提交**,并明确声明新参考点(宪法 IV)。

### Key Entities

- **候选记忆(Retrieved Memory)**:一条进入答题上下文的记忆,含正文、绝对事件日期(可能缺失)、来源会话标识。脚手架的输入单元。
- **TIMELINE 条目(Timeline Entry)**:一条有可解析日期的候选记忆在脚手架中的呈现,含序号、规范化日期、日期来源(原生 / 由相对表达推导)、对应记忆指针。
- **时间跨度(Interval)**:两个 TIMELINE 条目之间预先算好的时间差,含两端点序号与跨度值;粒度不足时降级为粗粒度表述。
- **脚手架块(TIMELINE Block)**:按时间升序排列的 TIMELINE 条目集合 + 时间跨度集合,作为整体附加到答题上下文;候选全无日期时整块省略。
- **Run 口径指纹(Regime Fingerprint)**:标识一次评测配置的字符串,须能区分脚手架开/关两种口径。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 脚手架在**零 LLM 调用**下完成——US1 全部验收可在无网络、无 GPU box 的环境中执行完毕,成本为 0。
- **SC-002**: 同一批候选记忆重复输入 100 次,脚手架输出 100 次逐字节相同(确定性 100%)。
- **SC-003**: 脚手架关闭时,答题上下文与当前实现的差异为 **0 字节**;非 temporal 类题目在脚手架开启时的差异同样为 **0 字节**。
- **SC-004**: 脚手架**不臆造**日期——在构造的缺日期 / 无锚 / 粒度不足的测试样例上,凭空产生日期或精确跨度的次数为 **0**。
- **SC-005**: 引擎目录改动为 **0 个文件**。
- **SC-006**: 端到端门产出的 verdict 同时给出:temporal 类准确率变化、配对显著性、overall 回退检查、噪声标尺臂差值、token 增量——**五项齐全**方可判定;缺任一项则结论标记为 inconclusive 而非 GO。
- **SC-007**: 名义可得上限已知并被明示:答题侧 temporal 38 题 ≈ 全量 **2.47pp**(且台账明确标注"实际远低"),verdict MUST 以此为分母讨论转化率,不得把任何增益外推超过该上限。
- **SC-008**: 无论结局,tracked 文档在收口后含本方向的最终状态,使下一位维护者**无需重跑**即可获知结论与归因。

## Assumptions

- **"用户" = 维护者**。本 feature 是评测口径 / adapter 特性,不面向终端用户,不改变 engram 对外 API 与 MCP 工具契约。
- **答题步属 host 侧,不属引擎**。脚手架落在评测 harness 内;其"可移植性"以文档化 pattern 形式交付,不作为引擎能力承诺。
- **沿用 014 已确立的类别门控方式**:temporal 类由数据集自带的类别标识判定,不新增分类器。
- **沿用现有 canonical recipe 作为 e2e 门的基础配置**,脚手架开关是唯一变量;不借机调整检索预算、top-k 或嵌入模型(否则归因失效)。
- **不引入付费云 reranker / 云 recall 模型**作为任何环节的得分手段(项目死规则)。
- **TIMELINE 是对上下文中**已有**信息的重组,不新增检索条目、不提高 top-k**;但它确实增加 prompt token,故 FR-013 强制实测该增量,以便判断收益属"提质"还是变相"加量"(maintainer 的 signal-not-volume 哲学要求可区分这两者)。
- **相对表达解析器只覆盖诊断中实际出现的模式**,不追求通用自然语言时间解析;覆盖不到的一律静默降级(FR-004)。
- **e2e 门在租用 GPU box 上跑**,该 box 是评测基础设施,引擎本身保持 local-first / 离线,不产生对它的依赖;box 凭据只走环境变量,绝不入库。
- **名义上限 2.47pp 来自答题侧 38/1540 的换算**,台账已标注"实际远低";本 feature 不承诺达到该上限,只承诺给出可信的 GO/NO-GO。
- **前置事实已核实**:C1「judge 口径补齐」已由 spec 007 落地(mem0-aligned judge 含部分给分与 ±14 天容差,且已是当前基线口径),故本 feature 不重复该工作。
