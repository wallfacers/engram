## 裁决口径

T011 审的是整个目标 proposal 是否满足 FR-008，而不是候选是否与问题“有一点相关”。只有
候选覆盖 reference answer 所需的全部信息时，`actions=[] + gap` 才是漏标；若复合问、
multi-hop 问或特定事件只被部分回答，`gap` 是正确的 fail-closed 标签。

因此：

- **T011 FAIL**：现有 `gap` 错误，候选已经足够回答 query，应有合法 action。
- **T011 PASS**：现有 `gap` 合理，候选不足以完整回答 query；不能为了过门改成 `KEEP`。

## 为什么这仍不是正式 T011 人审

- 原 `review.final.csv` 的机械结果是 `181/200 = 90.5%`，Wilson 95% CI
  `[85.64%, 93.83%]`；其中 137 行曾被启发式自动预填 `pass`，不是 200 行独立完整人审。
- `label.py` 未把 `gold_answer` 写入训练样本，实际审查表的该列 200/200 为空，无法按
  reference answer 核对完整覆盖。
- `review.py` 只导出前 5 个候选；下方的“candidates”不是正式输入的全部候选，也没有
  candidate id、rank、source lineage，不能据此生成合同有效的纠正 action。
- 原始收据摘要：`review.csv` sha256
  `49ab921ca4f9b625eb4c7cef7ffc04190fdd42c580d05f964869409a80f02520`；
  `review.prefilled.csv` sha256
  `f24d66b8dfeb0fb600c23eaa806073deef98ff0ddb15f69a040b4fd34b84bcc4`；
  `review.final.csv` sha256
  `f7a8e16e7cd7c40d4036430c792cf3d0801586fa8cb21bade477ee007c7d9881`。

另有两个独立合同阻塞项：当前标签器生成的 `gap.source_need` 为空，而 022 validator 要求
非空；`local_planner.go` 又把小写 gap kind 转成大写后与小写合同常量比较，所有合法 gap
都会被拒绝。因此即使下面 6 个 gap 语义合理，r1 标签仍不是合同合格训练资产。

代码层面另有一个能产生这 13 个 false-gap 症状的机制：`label.py` 只把 source id 与
gold source id 精确相交的 candidate 视为 required；来自另一 source 的等价答案句仍会被标
`actions=[] + gap`。本文没有 candidate/source id，不能把每一条都最终归因到该机制。

## 处置

`023-b20260803-r1` 不得进入 T015 正式训练。先修审查导出和 gap 合同映射，用同一冻结
200 sample id 完成带 gold answer、全部候选和 lineage 的独立复核；再修 false-gap 标签根因、
提升 build version、确定性重建，并重跑 T010–T013。不得删除失败样本、放宽 rubric 或把
部分回答改成 `KEEP` 来过门。
