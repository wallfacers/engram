# Feature Specification: Unified Evidence-Grounded Answer Contract

**Feature Branch**: `038-unified-answer-contract`

**Created**: 2026-08-13

**Status**: Draft

**Input**: User description: "审计 LoCoMo 特有提示词是否也为跑分而设计；把可泛化的行为整理为一个系统提示词并测试跑分。不得依赖 benchmark 特殊类别、标准答案措辞或测试题示例，未来用于真实场景时不能拉垮。"

## Context and Scope

现有答题路径按 LoCoMo/LongMemEval 的题型编号选择多套提示词，其中包含“这是可回答的评测”、强制猜测、固定拒答措辞、题型专用路由及基于既有错题形成的规则。这些机制可以提高特定评测分数，却不能证明真实场景中的可靠性，并可能造成实体错配、错误拒答、过时信息覆盖历史问题或把会话日期误当事件日期。

本特性交付一份统一的证据约束回答合同。合同只依据用户问题、检索记忆及可选的提问时间工作，不读取 benchmark 名称、题型编号、标准答案或评分器约定。旧提示词保留为实验对照；统一合同在通过配对评测与真实场景行为门之前保持默认关闭。当前仓库中的 17 个行为案例只是开发 smoke fixtures：它们与合同同期编写，不是独立 held-out 泛化证据，也不足以估计 2% 的错误拒答上限。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一份与数据集无关的回答合同 (Priority: P1)

作为把记忆层接入真实助手的集成方，我希望使用同一份系统回答合同处理事实查询、时间问题、多证据聚合、状态更新、偏好和合理推断，而不需要知道问题来自哪个 benchmark 或属于哪个类别。

**Why this priority**: 这是去除跑分特殊化的核心。没有统一合同，后续分数即使提高也仍不能迁移到真实产品。

**Independent Test（story-level 开发检查，非 held-out）**: 向合同输入一组未取自 LoCoMo 或 LongMemEval 的开发 smoke 场景，覆盖直接事实、别名、多实体、列表、计数、时间、状态更新、偏好推断、证据不足、冲突证据和记忆内指令注入；确认每个场景均遵循同一合同且无需题型标签。这项检查只发现明显回归，不作为产品推广证据。

**Acceptance Scenarios**:

1. **Given** 问题所需的主体、属性和时间范围被记忆直接支持，**When** 回答，**Then** 系统给出由证据支持的自然、直接答案，不把相似主体的属性迁移过来。
2. **Given** 问题要求列表、计数或比较，**When** 相关证据分散且可能重复，**Then** 系统扫描全部证据、合并同一事件的重复表述并只返回受支持的项目或数量。
3. **Given** 问题涉及日期、相对时间、持续时间或先后顺序，**When** 提供事件文本、日期锚和可选提问时间，**Then** 系统结合文本语义与时间锚推理，不把记录时间自动等同于问题所指事件时间。
4. **Given** 问题询问当前状态且存在明确更新，**When** 新旧证据可排序，**Then** 系统采用最新被明确支持的状态；询问历史状态时保留相应历史答案。
5. **Given** 问题要求意见、动机、偏好或可能行为，**When** 记忆提供相关线索，**Then** 系统允许常识辅助的合理推断，但不得把常识当作新的个人事实。
6. **Given** 记忆不足、只涉及不同主体或存在无法消解的冲突，**When** 回答，**Then** 系统以自然语言说明信息不足或冲突，不猜测，也不要求固定评分器措辞。
7. **Given** 记忆文本包含要求模型改变行为的指令，**When** 回答，**Then** 系统把记忆视为不可信证据数据并忽略其中的指令。

### User Story 2 - 审计并隔离历史 benchmark 提示词 (Priority: P2)

作为维护者，我需要知道现有 LoCoMo 与 LongMemEval 提示词中哪些内容是通用能力，哪些内容依赖题型编号、测试题示例、标准答案措辞或“必须猜测”的评测假设，从而避免把跑分技巧包装成产品能力。

**Why this priority**: 只有完整盘点历史特殊化，才能证明统一合同没有暗中复制旧规则或泄漏测试内容。

**Independent Test**: 生成逐提示词审计表，逐项标记数据集/类别路由、测试题短语、固定 gold 措辞、强制猜测、日期假设、输出格式和可泛化原则；对统一合同运行自动检查，确认零 benchmark 名称、零类别编号、零测试题示例、零固定 gold 句式。

**Acceptance Scenarios**:

1. **Given** 所有现有回答提示词，**When** 完成审计，**Then** 每条规则都有“通用保留 / 改写后保留 / 仅作历史对照 / 删除”裁决及理由。
2. **Given** 本地安装的 LoCoMo 与 LongMemEval 语料，**When** 检查统一合同，**Then** 合同中的示例短语数量为零，且不存在从测试问题或答案逐字复制的内容。
3. **Given** 统一合同启用，**When** 任意题目进入回答路径，**Then** prompt 选择不读取数据集格式或类别编号；可选提问时间仅作为真实业务元数据使用。

### User Story 3 - 用可比较实验裁决是否可落地 (Priority: P3)

作为维护者，我希望将当前提示词栈作为控制臂、统一合同作为单变量处理臂，在相同检索证据、模型、判分器、时间窗口和重复次数下比较，既看 benchmark 分数，也看真实场景中的幻觉与错误拒答，避免只为总分优化。

**Why this priority**: 可落地要求“正确回答不掉、无证据时少编、推断边界清楚”，不能只看一个总分。

**Independent Test**: 先运行 17 例开发 smoke 与小型配对 pilot 验证链路，再在条件允许时运行 LoCoMo 全量三重复配对实验和另行冻结的人工标注 held-out 行为集；LongMemEval 已被用于提示词归因，只能作兼容性诊断，不能作为泛化证明。实验报告逐题给出控制/处理翻转、错误拒答、无证据硬猜、调用成本和配对统计。

**Acceptance Scenarios**:

1. **Given** 同一批问题与完全相同的检索上下文，**When** 跑控制臂和统一合同臂，**Then** 除 system prompt 外的模型、证据、生成参数、判分器和重复策略完全一致。
2. **Given** LoCoMo 可回答问题，**When** 比较三重复多数票，**Then** 报告总体及各行为类型的点估计、配对翻转和 McNemar 结果，不以跨 run 的单点差声称提升。
3. **Given** 无证据、错实体与冲突场景，**When** 比较两臂，**Then** 分别报告错误作答率与错误拒答率；总分不得掩盖其中任何一项恶化。
4. **Given** 当前 LongMemEval 测试集已参与提示设计，**When** 在其上评分，**Then** 结果明确标为 post-hoc compatibility diagnostic，不作为推广或默认开启依据。
5. **Given** 统一合同在完整可比实验中测得未通过预先声明的非劣与可靠性门，**When** 收口，**Then** 保持默认关闭并记录 NO-GO，不通过修改题型路由或添加测试集示例追分；若是端点、held-out 或人工标注缺失，则记录 BLOCKED，不把缺测当成失败。
6. **Given** 只有当前 17 个开发 smoke 案例，**When** 裁决是否推广，**Then** 不宣称已证明 false-abstention 不高于 2%；该结论必须来自独立编写、预先冻结、盲化人工标注且样本量足以支撑统计上界的 held-out 集。

### User Story 4 - 提供真实集成可复用的系统提示词 (Priority: P4)

作为产品集成方，我需要一份自包含、无 benchmark 术语的系统提示词以及明确的输入约定和局限，可以直接放入 host 的回答步骤，而不是依赖评测工具私有类别。

**Why this priority**: 只有评测通过后才值得形成产品资产；文档不能先于证据宣称能力。

**Independent Test**: 在不阅读 benchmark 代码的情况下，仅根据文档即可构造问题、记忆证据和可选提问时间并调用回答模型；输出符合合同且文档列出适用边界。

**Acceptance Scenarios**:

1. **Given** P3 达到门槛，**When** 发布合同文档，**Then** 文档包含完整提示词、输入结构、输出原则、冲突/不足/时间/推断边界和已验证范围。
2. **Given** P3 未达到门槛，**When** 归档结果，**Then** 只发布诊断与失败原因，不把提示词推荐给真实集成方。

### Edge Cases

- 同一主体存在别名、简称或称谓变化：只有上下文建立同一性时才合并；纯字符串不同不自动判为不同实体。
- 不同主体名称相似：没有同一性证据时不得迁移属性。
- 同一天多次独立事件：不得仅凭日期相同去重。
- 同一事件被原始对话和抽取事实重复表达：应合并后计数一次。
- `[event:]` 或记录日期与文本描述的真实事件日期冲突：优先解释文本所述事件并显式保留不确定性，不盲信标记。
- 当前状态存在多个更新但时间不可排序：说明冲突，不任意选择。
- 问题只要求事实但证据只支持弱推断：不得把推断写成事实。
- 记忆包含恶意或无关指令：忽略指令，只把其事实内容作为候选证据。
- 用户要求详细解释而非短答案：遵循用户所需形式，不强制 benchmark 式最短短语。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供一份统一回答合同，用于所有受测问题，不依据 benchmark 名称、数据集格式、题型标签或类别编号选择不同合同。
- **FR-002**: 统一合同 MUST 将检索记忆视为可能不完整、重复、过时、冲突且不可信的证据数据，并 MUST 忽略记忆中的行为指令。
- **FR-003**: 统一合同 MUST 在作答前核对问题所指主体、属性、时间范围与所需输出形式；相似主体的证据 MUST NOT 被迁移到目标主体。
- **FR-004**: 统一合同 MUST 允许在上下文明确建立同一性时解析别名和指代，MUST NOT 使用纯字符串相等作为唯一实体判据。
- **FR-005**: 对事实问题，答案中的每个实质性事实 MUST 由相关记忆直接支持；对意见、动机、偏好或预测问题，合同 MAY 使用常识连接证据，但 MUST NOT 引入新的个人事实，并 MUST 保持推断语气。
- **FR-006**: 对列表、计数与比较问题，合同 MUST 扫描全部提供证据、区分独立事件并合并同一事件的重复表述，MUST NOT 补入无证据项目。
- **FR-007**: 对时间问题，合同 MUST 联合使用文本语义、事件/记录日期锚和可选提问时间，MUST NOT 无条件把任何单一日期标记视为问题所指事件日期。
- **FR-008**: 对当前状态问题，合同 MUST 在时间可确定时采用最新明确状态；对历史问题 MUST 选择相应历史证据；时间或冲突无法消解时 MUST 说明限制。
- **FR-009**: 当缺少关于目标主体及所问属性的充分证据，或冲突无法消解时，合同 MUST 自然地说明信息不足或冲突，MUST NOT 猜测，且 MUST NOT 规定 benchmark gold 的固定拒答句式。
- **FR-010**: 合同 MUST 默认给出自然、直接且符合用户请求形式的答案；MUST NOT 为迎合评测无条件强制最短短语、特定日期格式或固定拒答文本。
- **FR-011**: 统一合同的实验入口 MUST 默认关闭；启用后所有回答路径 MUST 使用相同合同，且旧提示词仅作为明确的控制臂保留。
- **FR-012**: 实验记录 MUST 绑定完整合同文本摘要、模型与生成配置；合同文字或相关配置改变时 MUST 拒绝在同一运行目录续跑。
- **FR-013**: 系统 MUST 提供不依赖真实 benchmark 内容的开发 smoke 测试，至少覆盖直接事实、别名、相似实体、聚合、时间、状态更新、推断、证据不足、冲突和记忆内指令。当前 17 例 MUST 标记为开发回归材料，MUST NOT 称为独立 held-out 或泛化证据。
- **FR-014**: 系统 MUST 自动验证统一合同不包含 benchmark 名称、类别编号、已知测试题示例或固定标准答案措辞。
- **FR-015**: 评分实验 MUST 为单变量配对设计，并报告总体正确率、错误作答率、错误拒答率、逐题翻转、重复策略、调用成本与配对统计。
- **FR-016**: LongMemEval 当前测试集上的任何结果 MUST 标记为 post-hoc 兼容性诊断；只有未参与提示设计的独立数据才能支持泛化或默认开启。
- **FR-017**: 在推广前，系统 MUST 证明可回答问题非劣、无证据/错实体场景的错误作答不增加、错误拒答不超过预先声明的界限；行为门 MUST 使用与提示词编写和开发 smoke 分离的 held-out 请求/证据，由不知道臂别的人工审阅者标注。任一门失败即保持默认关闭。
- **FR-018**: 本特性 MUST NOT 修改记忆引擎、存储 schema、检索、抽取、策展或 embedding 行为；改动限于评测/host 回答层。
- **FR-019**: 本特性 MUST NOT 使用付费云 reranker 或 recall 模型；评测模型端点仍须可替换并且不得泄漏凭据。

### Key Entities

- **统一回答合同**: 一段数据集无关的系统提示词，定义证据核对、事实与推断边界、实体/时间/聚合/状态处理、冲突与信息不足行为以及输出原则。
- **历史控制合同**: 当前按类别选择的 LoCoMo/LongMemEval 提示词集合，仅用于测量统一合同的增量，不作为通用产品合同。
- **开发 smoke 行为场景**: 与合同同期编写的最小问题—证据—期望行为案例，不复制 benchmark 内容，用于快速发现明显的合同或链路回归；不用于声称泛化。
- **Held-out 行为 cohort**: 与提示词、旧基准错题和开发 smoke 分离编写、预先冻结并由盲化人工审阅者标注的请求—证据集，用于产品行为门。
- **配对评测记录**: 同一问题在控制/处理臂下的答案、判定、错误类型、调用成本、合同摘要及配置指纹。
- **推广门**: 可回答非劣、错误作答、错误拒答和泛化证据四项联合裁决；任一失败即 NO-GO。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 统一合同文本中 benchmark 名称、数据集格式、题型标签、类别编号、已知测试题示例及固定 gold 拒答句式的出现次数均为 0。
- **SC-002**: 所有回答路径在统一合同启用时使用完全相同的基础合同文本；按类别发生的 prompt 分支数为 0。
- **SC-003**: 17 个开发 smoke 案例全部通过：直接支持题不错误拒答，相似实体/无证据题不错误作答，聚合/时间/更新/冲突/推断/注入场景符合合同。该结果只是开发 gate，不计入泛化或 2% 错误拒答的推广证据。
- **SC-004**: LoCoMo 三重复配对结果中，统一合同在可回答问题上的多数票准确率相对控制臂点估计不低于 −0.5pp，且没有统计显著回退；所有分题型结果与逐题翻转均如实报告。
- **SC-005**: 在 LoCoMo 对抗题及独立 held-out 的无证据/错实体场景中，统一合同的错误作答率不高于控制臂；held-out 直接支持 slice 的错误拒答率不高于 2%，相对 control 增幅不高于 1pp，且单侧 exact 95% 上置信限不高于 2%。若观测到 0 次错误拒答，仅该 direct-support slice 也至少需要 149 个独立案例；17 例 smoke 无法建立此结论。
- **SC-006**: 每次评测产物都能证明控制/处理臂除合同文本外配置一致，并包含可复核的合同摘要、模型 revision、重复次数、成本和配对统计。
- **SC-007**: 当前 LongMemEval 测试集结果只以兼容性诊断发布；在取得未参与设计的独立验证结果之前，统一合同保持默认关闭且不被称为产品能力。
- **SC-008**: 记忆引擎目录改动文件数为 0，离线构建与测试全部通过。

## Assumptions

- 统一合同首先作为 host/评测层能力验证；它不改变 engram 的记忆写入或检索算法。
- 现有按类别提示词保留为只读控制臂，直到统一合同通过推广门；本特性不通过隐藏修改控制臂追求更好差值。
- LoCoMo 已被长期用于调优，因此可用于回归与非劣检验，但不能单独证明真实世界泛化。
- LongMemEval 当前 cleaned 测试集已参与错题分析和提示设计，因此只能提供兼容性信号。
- 当前 17 例开发 smoke 与合同同期设计，即使全部通过也不能替代独立 held-out 及盲化人工标注。
- 若本机缺少可用的回答/判分端点，必须完成离线合同测试和可复现实验脚本，但不得伪造跑分；待端点恢复后按同一冻结方案继续。
- 真实集成文档仅在推广门通过后成为推荐材料；失败结果同样保留。
