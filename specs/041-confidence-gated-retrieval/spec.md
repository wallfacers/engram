# Feature Specification: Confidence-Gated Iterative Retrieval (置信度门控迭代检索)

**Feature Branch**: `worktree-041-confidence-gated-retrieval`

**Created**: 2026-08-14

**Status**: Draft

**Input**: User description: "每次提问都拖入全量 top-k 上下文太浪费。是否有 Agent ReAct 循环，不用每次读那么多，而是「读到足够回答这个问题就停」，按需取量，替代大批量读取。"

## 背景：为什么是「置信度」而非「检索分数」

040（自适应检索深度）用**检索分数序列的 gap-knee 拐点**决定深度，判为 **NO-GO**——因为 top-k 30→150 的净 +25 题（1.62pp）= **56 题救回 − 31 题害**，其中 56 题里 42 题是「关键证据已被召回、但 answerer 因上下文量不足而答错」，只有 11 题是「关键证据未被召回」。gap-knee 只能感知「分数拐点」→ 只救得到那 11 题，r 上限 20%，低于保住 90pp 所需的 45% 门槛。

**转折发现（041 的基石）**：对这 56 题在 top-k 30 下的 predicted 文本做「自信 vs 犹豫」分析，发现 **89% 的答错是「犹豫的」（55% 强犹豫 + 38% 弱犹豫），仅 7%（3 题）是「自信地错」**。这推翻了「信息不足时会自信地瞎答」的担心（029 正是栽在「让模型自主判断」上），并给出一个可操作的上限：若「犹豫 → 加深检索」能救回所有「犹豫的错题」，理论上限 **91.75%**（> 当前 90.13%，+1.6pp），且平均 top-k 收敛到 ~31（**省 4.8× 预算**）。

本 feature 的机制区别于 040：**不再看检索分数，而是看 answerer 生成过程中的确定性不确定信号（犹豫/置信度）**，用「犹豫则加深、自信则停」的迭代循环替代固定大预算。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 犹豫信号检测：把 answerer 的不确定变成可机读的确定性信号 (Priority: P1)

评测维护者需要先证明一件事：answerer 在「信息不足、会答错」时，其生成过程（thinking + 最终答案）表现出**可稳定检测的犹豫/不确定信号**，且该信号能区分「会答对」与「会答错」。这是整个 feature 的生死前提——若信号不存在或无法确定性提取，迭代机制就是空中楼阁。

**Why this priority**: 040 的「89% 犹豫」是后验人工分析，尚未被固化为一个确定性、可复现的检测器。在写任何「加深检索」逻辑之前，必须先证明「犹豫」可以从 answerer 的正常生成中流式提取，并给出它对「答对/答错」的区分度（准确率/召回率/混淆矩阵）。这一步只读、零模型成本，证伪即停。

**Independent Test**: 在固定记忆库、问题集、answerer 与已知「答对/答错」标签上，运行一个只做流式扫文本、不做任何检索改动的检测器，产出逐题犹豫判定 + 区分度汇总。不依赖后续迭代实现。

**Acceptance Scenarios**:

1. **Given** 一组已作答的问答（含 answerer 的 thinking 与最终答案）与答对/答错标签, **When** 维护者运行犹豫信号检测器, **Then** 检测器对每题给出确定性的犹豫判定（犹豫/自信，可带强度），且同一文本重复运行得到完全相同的判定。
2. **Given** 犹豫判定已产出, **When** 维护者查看汇总, **Then** 报告给出「犹豫题中答错的占比」「自信题中答对的占比」等区分度指标（混淆矩阵），据此判断信号是否具备门控价值。
3. **Given** 信号区分度不达预设门槛, **When** 维护者据此判定, **Then** 该方向判为不可行，不进入迭代实现，且不改动任何检索路径。

---

### User Story 2 - 置信度门控迭代检索：犹豫则加深，自信则停 (Priority: P1)

集成方希望每个问题只消耗「够用」的证据量：先用浅预算（小 top-k）检索并作答，若 answerer 在生成中表现出犹豫/不确定，则加深检索（读更多）重答；若自信，则停在浅预算。以「读到足够就停」的迭代循环，替代当前「所有问题统一读满 top-k 150」。

**Why this priority**: 这是 feature 的核心价值——用「按需取量」替代「大力出奇迹」的固定大预算，且机制锚定 answerer 置信度而非检索分数（040 已证伪后者）。与 US1 并列 P1，但实现严格排在 US1 通过之后。

**Independent Test**: 在固定记忆库、问题集、answerer、judge 与聚合口径下，分别以「固定深度 150」与「confidence-gated 迭代」跑完整评测，配对对比答案正确率与平均证据消耗。迭代机制默认关闭，关闭时行为与当前一致。

**Acceptance Scenarios**:

1. **Given** confidence-gated 迭代检索处于关闭状态, **When** 系统处理一个问答请求, **Then** 其检索与作答行为与当前固定深度完全一致（逐字节无变化）。
2. **Given** 迭代机制开启, **When** 系统处理一个浅预算下即能答对的问题（answerer 自信）, **Then** 系统停在浅预算，消耗的证据量显著低于固定深度 150，且答案正确。
3. **Given** 迭代机制开启, **When** 系统处理一个浅预算下信息不足、answerer 犹豫的问题, **Then** 系统加深检索并重答，救回关键证据，答案不再因上下文量不足而错。
4. **Given** 迭代机制开启, **When** 系统以完整评测口径跑批, **Then** 平均证据消耗相比固定深度 150 显著下降，且答案正确率不出现统计显著的下降（配对比较）。

---

### User Story 3 - 阈值校准：犹豫信号到「加深」决策的标定 (Priority: P2)

集成方需要迭代机制不失控：犹豫信号判定「多强才算需要加深」的阈值必须被标定，避免「过度加深」把省下的预算又烧回去，也避免「漏判犹豫」丢掉本可救回的题。校准基于 held-out 数据，目标是预算与正确率之间的稳健平衡。

**Why this priority**: 论文（When Should Active RAG Retrieve）警告 nominal 阈值在 held-out 数据上会因 calibration failure 而超预算。阈值不标定，迭代机制要么退化成固定大预算，要么救不回题。它是 US2 可用性的保障，但可在 US2 机制跑通后单独调优。

**Independent Test**: 在固定口径下，用一部分 held-out 问题标定阈值，再用另一部分验证：加深决策率、平均预算、正确率三者同时满足目标区间。可独立于 US2 的核心循环单独评估。

**Acceptance Scenarios**:

1. **Given** 阈值标定完成, **When** 系统在 held-out 验证集上运行, **Then** 加深决策率落在目标区间内，不因阈值失准而普遍加深（退化为大预算）或普遍不加深（救不回题）。
2. **Given** 阈值标定完成, **When** 系统跑完整评测, **Then** 平均预算与正确率的组合不劣于固定深度 150 基线（正确率不显著下降、预算显著下降）。

---

### Edge Cases

- answerer 不输出 thinking（或 thinking 被关闭）时，犹豫信号从何而来？（应回退到固定深度，而非强行加深或收缩——宪法 V。）
- answerer 反复犹豫、每一轮加深都仍犹豫，可能无限迭代？（必须设最大轮数/最大预算上限，超限即停。）
- 一个「自信地错」的题（040 显示约 7%）无法被犹豫信号救回，迭代机制是否承认这个盲区？（应在诊断中显式报告该盲区占比，不夸大可救上限。）
- 三个检索信号（语义/关键词/实体）中某一路不可用时，迭代与信号检测是否仍正确降级而不报错？（宪法 V。）
- 浅预算下关键证据恰好被召回但 answerer 未利用（上下文量不足），与「关键证据根本未召回」是两种不同失败，加深检索对后者的收益更直接——机制是否对两者都成立？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供默认关闭的 confidence-gated 迭代检索机制；关闭时检索与作答行为 MUST 与当前固定深度逐字节一致。
- **FR-002**: 犹豫信号 MUST 是确定性提取的（同一 answerer 生成文本 → 同一判定），判定「是否加深」MUST 依据该信号，而非让模型自主判断（绕开 029「自主决定不可靠」的教训）。
- **FR-003**: 犹豫信号 MUST 从 answerer 的正常生成中流式提取（thinking 与最终答案），不得引入「先无检索答一次再判置信度」的额外 closed-book probe（规避 Know Before You Fetch 的额外 pass 成本）。
- **FR-004**: 迭代机制 MUST 设保守上限（最大轮数与最大预算），超限即停，不得因反复加深而无限膨胀或超出固定大预算。
- **FR-005**: 当犹豫信号不可得（如 answerer 不输出 thinking、信号通道失败）时，系统 MUST 回退到固定深度，而非强行加深或收缩。
- **FR-006**: 诊断工具 MUST 对每个评测问题给出犹豫判定与「答对/答错」的区分度指标（混淆矩阵 + 准确率/召回率），并显式报告「自信地错」这一信号盲区的占比。
- **FR-007**: 迭代与信号检测 MUST 在检索信号缺失/失败时独立降级，不整体报错（宪法 V）。
- **FR-008**: 任何检索行为的改动 MUST 在合并前以「同记忆库、同问题集、同 answerer、同 judge、同聚合口径」配对评测，证明答案质量不出现统计显著回退（宪法 IV）。

### Key Entities *(include if feature involves data)*

- **犹豫信号**：从单次 answerer 生成（thinking + 最终答案）中确定性提取的判定，取值「犹豫/自信」并可选带强度；是迭代决策的唯一输入。
- **检索预算阶梯**：浅预算与深预算（及可选的多级预算）的配置，定义「读到多少」的档位。
- **迭代决策记录**：针对单个问题的「停/加深」判定序列、每轮使用的预算、以及最终答案的来源轮次，用于可复现审计。
- **校准阈值**：把犹豫信号强度映射为「是否加深」的标定参数，基于 held-out 数据冻结。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 犹豫信号检测器能在「会答错」与「会答对」两类题之间给出统计显著的区分度（具体阈值与显著性口径在诊断阶段按数据冻结），且对同一文本的判定完全确定性。
- **SC-002**: 迭代机制开启后（仅当 SC-001 通过），平均每个问题的证据消耗相比固定深度 150 **显著下降（目标收敛到 ~31，即省 ~4.8×）**，且答案正确率相对当前基线（90.13%）无统计显著下降（配对比较）。
- **SC-003**: 关闭迭代机制时，系统在完整评测上的结果与当前基线完全一致（逐题无差异），证明新机制是纯 opt-in、无侵入。
- **SC-004**: 诊断显式报告「自信地错」的盲区占比，且不夸大理论可救上限（91.75% 是完美信号下的 oracle ceiling，非承诺值）。

## Assumptions

- **信号形态**默认采用「流式犹豫检测」：在 answerer 正常生成中（thinking 已在 content 内）提取犹豫/不确定信号；log-prob 置信度作为可选增强（需 answerer 端点暴露 log-prob，配置成本更高），不在首版硬性依赖。
- **迭代结构**默认两轮（浅 → 深），多轮渐进（30→60→90→150 阶梯）作为后续扩展，不在首版承诺。
- **正确率永远优先于省预算**：任何省预算的实现若导致正确率统计显著下降即判失败；「省 4.8×」是目标上限而非硬门槛。
- 本 feature 只在 eval harness 层（`cmd/locomo-bench`）实现并验证，**不触碰引擎**（`memory/ embedding/ provider/ store/ internal`），符合宪法 II；生产接线（MCP/CLI/SDK）是独立的后续 feature（同 023 planner 的接线教训）。
- 本 feature 只作用于「检索之后、作答之前/之中」的证据量与迭代决策，不触及写入侧（事实抽取、curation）——写入侧已在既往 feature 中反复证伪。
- 所有新机制默认关闭；转正（设为默认）是独立后续决策，须满足宪法 IV 的评测回归门禁。
- 「不出现统计显著下降」沿用项目既有配对显著性口径（同批、同 judge、多次作答多数票），具体阈值在 plan 阶段冻结。
- 背景证据：040 verdict（`docs/evaluation/reports/040-adaptive-topk-verdict.md`）+ 三篇论文综合（TeaRAG 2511.05385、When Should Active RAG Retrieve 2607.24010、Know Before You Fetch 2606.29959），结论见 `memory/iterative-retrieval-paper-synthesis.md`。
